# Эксперименты H3: модель, кэш, продолжение

Добавлено 2026-10-21 по просьбе пользователя попробовать квантизацию и подходы из присланных workflow ради качества и скорости. Реализация не означает приёмку новых весов. BF16 и защищённые рецепты остаются исходным вариантом; GPU на момент интеграции недоступен.

## Рабочий путь

`render-experiments.mjs` → `settings.profile` / `settings.render_options` → `store.py` → `gpu_form_fields` → worker capability → GPU API preflight → `h3graph/core.py` / `apply_render_options`.

- Профили: исходный BF16; full INT8 ConvRot; pruned INT8; pruned INT4 W4A8; Cobijada hybrid pruned BF16; Singularity v2 INT8.
- Во всех профилях энкодер остаётся полным Qwen3-VL BF16; VAE и заданные шаги/размер не меняются. Это позволяет сначала сравнить одну переменную — DiT. Экономия памяти DiT не равна экономии всей системы; CPU-энкодер — отдельный выбор с большим требованием RAM и возможным замедлением.
- Опциональные LoRA: ORB360 step1500, CardSpin v2, Wushu Ref2VA v7. Имена, commit, размер и SHA-256: `app/render_assets.json`.
- LoRA не смешивается со стилевыми/Character Swap без разрешённой комбинации. Wushu v7 при `combat` заменяет только прежнюю action-LoRA, сохраняя physics; сама по себе — отдельный адаптер. Нельзя считать FL2VA и Ref2VA версии взаимозаменяемыми. ORB360 требует соответствующего описания облёта; триггер добавляется внутри `detailed_description` официального IR.
- `workflow_euler` — Euler/simple с полным заданным числом шагов. Это не Turbo и не имитация TaoMate/SMD.
- SOL attention опционален: проверяются узел, его схема и метод. Approximate attention не гарантирует равное качество.
- SAFE/FAST/CUSTOM/off сохраняются как выбрал пользователь. Reset эксперимента не меняет cacheMode. Фактические reuse/full calls уже сохраняет существующий cache telemetry.
- Отсутствующие веса и узлы отклоняются до upload/постановки на GPU; выбор не заменяется BF16 молча. Worker требует `render_profiles_v1.version=1`; прежний сервер не сможет проигнорировать новые поля.
- Без эксперимента новые form-поля не отправляются. Старые fingerprint и golden-графы сохраняются. Для повторного редактирования задания восстанавливаются его model/options; загрузка старого задания очищает предыдущее экспериментальное состояние.
- История получает `director.render_profile`: фактические имена модели/энкодера и `quality_verified=false`. Это техническая запись выбранного графа, не заключение о визуальном качестве.

## Возможности

GPU `/api/capabilities` → `render_profiles_v1`: каталог, наличие файлов в UNETLoader/CLIPLoader/LoraLoader, поддержка SOL и CPU. Mac `/api/studio/render-options` передаёт живую доступность; при отключённом GPU показывает каталог с недоступными вариантами. Наличие файла и успешная загрузка/генерация — разные проверки.

## Установка выбранных весов

Только на существующем GPU с установленной Studio, существующим приватным HF curl config (владелец процесса, mode 600) и пустой ComfyUI очередью:

```bash
# Только план, без сети/изменений:
python scripts/h3_install_render_assets.py --profiles int8_full --adapters orb360,wushu_r2v_v7
# Установка на выбранном GPU:
python scripts/h3_install_render_assets.py --root /workspace/h3 --profiles int8_full --adapters orb360,wushu_r2v_v7 --apply
```

Около 34,95 GB для этой выборки плюс резерв 5 GiB. Базовые BF16/энкодер должны уже быть установлены обычным установщиком. Другие профили выбираются явно; не скачивать всю подборку. Загрузчик сериализуется файловым lock, использует HF auth из приватного curl config, возобновляет `.part`, проверяет размер/SHA до переименования. Существующий отличающийся файл не перезаписывает. Повторно проверяет очередь перед установкой. Сервисы не перезапускает. После установки обновить список возможностей, построить граф против реального `/object_info`, затем выполнить ограниченную пробу.

Новый код API и Mac должен быть развёрнут обычным обновлением Studio. Не восстанавливать снимок поверх существующего непустого сервера. Не использовать исторические host/port как текущие. Перезапуск Mac разрешён запросом на внедрение, но отложен, пока есть неоднозначные `running`/`queued_gpu` и невозможно проверить их на отключённом GPU.

## Продолжение по видео и звуку

В Сюжете → Сборка → Цвет и параметры есть опция «продолжать по видео и звуку». По умолчанию выключена, старое продолжение с картинки остаётся.

Для шота «Продолжение» требуется принятие текущего предыдущего дубля: результат QC `accept/adapt_next` либо ручное принятие, привязанное к тому же job. Проверяется capability `continuation_v1`. Готовый MP4 предыдущего задания импортируется через `/api/jobs/{job_id}/reference-video` с дедупликацией и подаётся последним видео с ролью «Продолжение»; фото героев сохраняются. Frame-0 guide из одиночной картинки не добавляется рядом с video guide. Исходный MP4 и временное состояние референсов сохраняются.

В новом задании `continuation_trim_frames=22` — локальное указание монтажу, допустимое только с настоящим продолжением. Concat сцены и всего фильма читает маркер задания и срезает первые 22 кадра вместе с тем же участком аудио. При наличии обрезки используется однократное перекодирование, проверяется итоговая длительность и наличие звука. Старые задания без маркера не обрезаются. После удаления контекста каждый такой шот короче примерно на 0,92 секунды; фактическая длительность фильма показывается после сборки. Это не потоковый AV-KV runtime TaoMate.

Синтетические MP4 со звуком проверяют монтаж, но не сохранение лица, движения, света и голоса на настоящем H3. Каждый реальный стык нужно просмотреть; QC/ошибка не должны автоматически порождать повторный платный рендер.

## Что намеренно не включено

TaoMate/SMD few-step требуют своих баз/расписаний/runtime и отдельной проверки; GGUF — другого загрузчика; готовые INT8+Turbo+ControlNet workflow не заменяют наш граф. Deno не скопирован и целиком не установлен (GPL); взяты функциональные идеи, а код интеграции собственный. Безусловная очистка VRAM и загрузка Whisper рядом с H3 не добавлены. Измеренный прирост скорости и визуальная приёмка отсутствуют до реальных рендеров.

### Замена по видео: откуда 40–58 мин (Claude, 02.11.2026)

Сравнение по `studio.sqlite3`, только `cache_mode=safe`, `mode=replace`, BF16 24–25 шагов, ref max:

| Что | Задания | Сэмплинг |
|---|---|---|
| 10 с, 0,6 Мп, звук в H3 | 1 задание | 1056 с |
| 11 с, 0,7 Мп, звук в H3 | 1 задание | 1646 с |
| 15 с, 672×1216, **без** звука исходника в H3 | 2 задания | 1407–1460 с |
| 15 с, 640×1152–736×1280, **со** звуком в H3 | 4 задания | 2335–2947 с |

1. Длина части: 15 с против 10 с при тех же настройках ≈ ×2,2. `video_swap_plan` резал до 15 с — теперь до 10 с.
2. `use_video_audio` при `keep_source_audio`: звук исходника шёл референсом через каждый шаг (+60–100 %), а потом
   заменялся оригиналом. Store теперь сам выключает его при `keep_source_audio` без своих аудиофайлов.
3. «Model Initialization» перед первым шагом 9,6–12,6 мин против 75 с в октябре: модели перечитывались с диска
   Vast (~200 МБ/с) после каждого переключения H3 ↔ Qwen-Image. `--high-ram` дал 2 мин 16 с, но на хосте с 1 ГБ свопа
   повесил сервер (load 41, 488 с/шаг) и **откачен** (`eeb2c5a8`); `verify_h3_server.sh` теперь ловит его при малом свопе.
   Рабочее лечение: группировка очереди по тёплой модели (`7ae3a4d5`), GPU-ключевые кадры Qwen-Image убраны (`8c2d74f5`).
4. Шаг ≈ 117 с (640×1152, 15 с, видео + 3 картинки max) совпадает с октябрьскими 2335 с — сервер не медленнее.
   Кэш `fast` быстрее в 3–4 раза, но заметно теряет качество картинки.
5. Встроенный кодировщик Qwen3-VL-32B — часть H3 (векторы текста и референсов), убрать или обойти его нельзя.
   Qwen-режиссёр (переписывал промпт) выключен с 24.10.

Не проверено: `ref_image_size=match` на замене по видео (на 5 с шотах −13–22 %, кадры почти одинаковы) — нужен A/B
одной части 10 с с тем же seed.
Не проверено (сервер потерян): Cobijada pruned BF16, Singularity pruned, SMD 8-step, kitchen attention, turbo + ref-match, качество turbo в движении.
