# H3 Studio — структура кода

## Повторный прогон Motion Director

План повторного прогона доступен через POST `/api/studio/motion-director/rerun-plan` и MCP `motion_director_rerun_plan`. Он распространяет устаревание по движению, звуку и ссылкам на результаты; не отправляет рендер. Незатронутые сегменты требуют отдельной сверки версий кэша перед повторным использованием.

## Английский интерфейс (08.11.2026)

Разметка, модули и сервер пишут по-русски. `preview/h3-director/dom-translate.mjs` (его грузит `studio-rail.mjs`, то есть
каждая страница) в режиме EN переводит всё, что попадает на страницу: текст, `title/placeholder/aria-label/alt`, `<title>`,
`confirm/alert/prompt` — по словарю `i18n/en.json` (русская фраза → английская; фразы вокруг вставленных значений
сопоставляются по частям, длинные первыми). Если после замены остаётся русский — это текст пользователя (промпт, имя
сцены), он не меняется. Поля ввода и `[data-no-i18n]` не трогаются, в `<code>/<pre>` — только целая фраза. Первый показ ждёт
словарь (`studioBoot.hold`), поэтому русский не мелькает. Язык: `locale.mjs` (`h3-studio-locale` в localStorage, иначе язык
браузера), переключатель RU/EN и строка автора — внизу левого меню; смена языка перезагружает страницу. Текст из CSS
(`content:`) переводится правилами `html[lang="en"]` рядом с исходными.

## Свои воркфлоу ComfyUI (07.11.2026, Claude)

`local_studio/user_workflows.py`, страница `preview/h3-director/workflows.html` (+ `workflows.mjs/css`). Отдельная полоса
рядом с H3: граф пользователя не проходит через `app/graph.py` и не меняет принятый рецепт.

- **Импорт**: POST `/api/workflows` {name, graph (формат API), params?}. Файл редактора (nodes/links) отклоняется с подсказкой
  «Workflow → Export (API)». Из ComfyUI без файла: кнопка моста «⇪ Воркфлоу в Studio» кладёт граф в
  `output/.h3-graphs/workflows/`, Studio читает `/h3/studio/workflows` (GET `/api/workflows/comfy-inbox`, POST `…/{id}/import`).
- **Форма**: `detect_params` — загрузчики (`LoadImage`, `LoadVideo`, `VHS_LoadVideo`, `LoadAudio`…), текстовые входы (негатив — по
  связи с `negative` сэмплера), `seed/noise_seed` открыты; `steps/cfg/width/…` найдены, но скрыты. PUT с `expected_revision`
  меняет видимость и подписи. Хранение: `<данные Studio>/workflows/wf_*.json`.
- **Запуск**: POST `/api/workflows/{id}/run` {values, count 1–4}. Открытые входы — только они; медиа — asset_id библиотеки с проверкой
  SHA-256; пустой seed — случайный, при count>1 — seed+i. Квитанции `workflow_jobs` (SideQueueRules): загрузка в верх `ComfyUI/input`
  как `studio_<sha>.<ext>`, `filename_prefix` → `studio_workflows/<id>`, проверка по `/object_info`, один POST `/prompt` с
  `extra_data.studio_workflow_job`; потерянный ответ → сверка, без повтора. Диспетчер: kind `workflow`, `GPU_MODEL=custom`, Pause
  держит; во время прямой отправки stage-loop H3 ждёт. Результаты — `results/workflows/<job>/`, отдача с проверкой хеша.
- **Агенты**: MCP `workflow_list`, `workflow_get` (форма с типами), `workflow_import`, `workflow_run` (gpu_gate, в код-режиме только с gpu=true),
  `workflow_jobs`, `workflow_job_get`.
- **Граф (фаза 2)**: `workflow-graph.mjs` — узлы колонками по глубине, связи кривыми; клик по узлу — правка любого значения
  (связи и состав узлов здесь не меняются, чтобы не оставить висящую связь). PUT `/api/workflows/{id}/graph` {expected_revision, graph}:
  та же запись, следующая ревизия, выбор видимости/подписей сохраняется для входов, которые остались. «Открыть в ComfyUI» →
  `comfyui.html?wf=<id>`: POST `/api/workflows/{id}/open-in-comfy` кладёт граф во входящие моста с `studio_id`, настоящий редактор
  ComfyUI открывается во фрейме с `?h3_workflow=<id>` (вкладка «Studio wf_… имя»); «⇪ Воркфлоу в Studio» возвращает его с тем же
  `studio_id`, во «Из ComfyUI» появляется «Обновить «имя»» (import с `target`). Нужен обновлённый мост на GPU.
- **Узлы и модели (фаза 3)**: `local_studio/comfy_manager.py`, `comfy-nodes.html/.mjs`. Опись живого ComfyUI: пакеты из
  `/object_info` (`python_module`), файлы из `/models/<папка>` (кэш 60 с). Манифест пользователя `<данные Studio>/comfy/manifest.json`:
  пакет = https-git + полный коммит + pip только `пакет==версия`; модель = папка + имя + https + SHA-256. Состояние каждой записи —
  на GPU / ждёт установки. «Применить на GPU» (POST `/api/comfy/manifest/apply`, только со страницы Studio) — фиксированный runbook
  `comfy_manifest` в `compute/manager.py`: `scripts/h3_comfy_manifest_apply.sh` копирует манифест и `install_comfy_manifest.py`
  на текущий сервер, ставит (чужая версия пакета или файл с другим SHA → стоп), перезапускает h3-comfyui только если что-то
  поставилось и очередь пуста. `h3_new_server.sh` применяет манифест на каждом новом сервере.
- **Первый запуск (фаза 4)**: `local_studio/setup_status.py`, `setup.html/.mjs`: Python, папка данных, ffmpeg, GPU API, ComfyUI, мост,
  текущий сервер, SSH-ключ, MCP у Claude/Codex — у каждого пункта способ исправить; адреса GPU/ComfyUI сохраняются в
  `<данные>/settings.json` (`config.py` читает его, если LaunchAgent не задаёт `H3_GPU_API_URL`/`H3_COMFY_URL`). Установщик для
  других: «Install Studio.command» в корне репозитория (`docs/guides/STUDIO_INSTALL.md`)
  в конце открывает `/setup.html`.
- **Агенты**: ещё `workflow_graph_update`, `comfy_inventory`, `comfy_manifest`, `comfy_manifest_add_node`, `comfy_manifest_add_model`
  (только манифест; установку запускает пользователь кнопкой), `studio_setup_status`.
- Меню: «Инструменты → ComfyUI» (Свои воркфлоу, Редактор графов, Узлы и модели) и «Первый запуск».
- **Правка графа Studio (08.11.2026, Claude)**: общий движок `app/graph_ops.py` — операции `set`, `link`, `unset`, `add_node`,
  `remove_node` (bypass ведёт связь мимо), `replace_node`, `add_lora`, `title`; `$ref` — узел, добавленный в той же правке. Всё
  сверяется с живым `/object_info` (тип и диапазон, шаг INT, список файлов/семплеров, тип связи, циклы); турбо/дистилл/квантизованные
  веса отклоняются (`quality_problems`). Ничего не знает о конкретном пакете — сторонние узлы (H3 Continuity Studio и др.) правятся так же.
  `local_studio/comfy_schema.py` — общий кэш `/object_info` (60 с; без ComfyUI правка не применяется) и API `/api/comfy/classes[?q=]`,
  `/api/comfy/classes/{class}`, `/api/comfy/graph/check`, `/api/comfy/graph/apply` (сухой прогон).
  Воркфлоу: POST `/api/workflows/{id}/edit` {expected_revision, ops, note, dry_run} → следующая ревизия; прежняя — в
  `<данные>/workflows/versions/<id>/r<N>.json`; GET `…/versions[/{rev}]`, POST `…/restore` (возврат = новая ревизия).
  `local_studio/job_graphs.py`: граф H3-задания копируется в `<данные>/job-graphs/<job>.json` по завершении (worker `on_completed`)
  и при каждом чтении, поэтому GET `/api/jobs/{id}/graph` и POST `/api/workflows/from-job/{id}` / `from-recipe/{id}` работают и
  после снятия сервера (рецепты до 08.11 в архив не попали — 409 с причиной). Правка H3-задания (`job_graph_edit`) принимает те же
  `ops`, но новые файлы весов там по-прежнему запрещены: LoRA — через копию задания в «Свои воркфлоу».
  UI: `workflow-graph-edit.mjs` (инспектор по схеме: выпадающие списки из `/object_info`, связи только совместимых типов,
  «＋ Узел», «＋ LoRA», «Заменить…», «Удалить», отмена, «Сохранить ревизию N»), `workflow-versions.mjs` («Отличия», «Вернуть»),
  кнопка «Из задания или рецепта» и «⎇ Граф в свои воркфлоу» на карточке задания (`comfy-edits.mjs`).
  MCP: `workflow_graph_edit`, `workflow_versions`, `workflow_version_get`, `workflow_restore`, `workflow_from_job`,
  `workflow_from_recipe`, `comfy_node_search`, `comfy_node_class`, `comfy_graph_check`; `job_graph_edit` с `ops`.

## Постановка на плане (31.10.2026, Claude)

`local_studio/staging.py`, POST `/api/staging/compile`, MCP `staging_compile`. Агент ставит героев, предметы и декор на
план в метрах (x вправо, y от фронта декора, facing 0° = +y), задаёт ось (пара героев) и установки камеры (позиция, высота,
объектив, на что смотрит, `eye_level_of`). Камера-обскура с реальным углом зрения объектива для 9:16/16:9 (полный кадр,
обрезанный до формата) вычисляет для каждого шота сторону экрана, глубину, крупность героя (рост / высота кадра на его
дистанции), направление взгляда и кто кого закрывает. Ошибки: камера пересекла ось без `crossing`, герои поменялись
сторонами, заявленная крупность расходится с реальной больше чем на ступень, герой шота вне кадра; предупреждения —
высота камеры против уровня глаз героя, закрытие, правило 30° (тот же герой с угла < 30° и крупностью ±1 ступень). На шот — английская строка постановки для first_frame/промпта, на сцену —
превиз сверху (SVG). `scene_draft` принимает `staging`: его ошибки блокируют сцену, ответ отдаёт строки по шотам. Взгляд
вверх/вниз и высота предметов в расчёте закрытия не учитываются.
Карточка сцены агента (`agent-dock.mjs`) показывает «Превиз постановки» (`scene-previz.mjs`): по открытию считает `scene.staging` на `/api/staging/compile` и выводит план картинкой и строки/замечания по шотам; метка «в пакете идеи» — при `idea_id`. Инструкции MCP-сервера ведут агента «франшиза + идея» по маршруту idea → idea_pack_build → staging_compile → scene_draft.

## Пакет идеи (31.10.2026, Claude)

`local_studio/idea_pack.py`: «франшиза + идея» → один набор референсов и один вид всех сцен идеи (по образцу банка
персонажей MovieAgent и визуальной памяти VideoMemory). POST `/api/franchises/{fid}/ideas/{eid}/pack` читает карточку идеи
ЭТОЙ франшизы и берёт героев, костюмы, предметы и места, названные в её тексте (в любом падеже), из паспорта и библии
через `franchise_profile.resolve_shot`; добавляет стилевые плашки франшизы, `style_lock` (style, строки лука, режиссура
по умолчанию, 9:16, English), одобренные правила и режим рендера. Картинки идеи — только по выбору агента и только в
неличностных ролях; листы из двух половин (`scene_frames.split_panel`) — только для чтения; картинка библиотеки — с причиной,
фото героя оттуда не берётся. Пакет хранится в `<данные Studio>/idea-packs/<fid>__<eid>.json` с ревизией; новая ревизия
карточки делает его `stale`. `POST …/pack/check` — проверка сцены. MCP: `idea_pack_build`, `idea_pack_get`; `scene_draft`
с `idea_id` отклоняет чужой референс, роль/владельца не из пакета, героя вне состава, другой style или mode. Маршрут
`studio_playbook workflow=idea`. Проверка стоит на пути агента (scene_draft); холст и сборка сцены `idea_id` пока не хранят.

## MiniMax H3 Motion Director (эксперимент, 30.10.2026)

Обновление 31.10.2026 (Claude). Сервер: `scripts/install_h3_motion_director.sh` — пин v1.2.0 + `scripts/patches/motion-director-kwargs.patch`
(официальный `MiniMaxH3ReferenceToVideo.execute` на нашем ComfyUI принимает аргументы в ином порядке) + torchaudio под torch venv;
ставится шагом 4b `h3_new_server.sh`, проверяется `verify_h3_server.sh`. Кэш сегментов узел держит в
`output/minimax_seg_cache/<ID узла>`; Studio даёт узлу ID `md_<sha16(scene_id)>` (`motion_jobs.director_id`), поэтому кэш свой у каждой сцены.
`GraphPlan.run_selection(previous)` сравнивает отпечатки и позиции сегментов с последним завершённым прогоном сцены
и заполняет `runSelection`; `MotionQueue.cached_on_gpu` проверяет HEAD `/view` файлы `seg_NNNN.pt`/`.audio.pt`, без них — полный прогон.
`Execute.full_run` — принудительно всё. `metrics_json` квитанции: `run_selection`, `gpu_seconds`, `gpu_seconds_per_video_second`.
Редактор умеет менять состав (выше/ниже/дублировать/удалить); первый сегмент теряет непрерывность.

`motion-director-editor.mjs` открывается кнопкой «Непрерывная сцена · Motion Director» в разделе сборки.
Окно привязано к scene_id на момент открытия: читает подготовленный агентом план, редактирует промпты,
длительности (кроме Source Video), seed/шаги и входящую непрерывность. Режим и состав refs сохраняются.
Сохранение сравнивает ревизию; запуск разрешён только для сохранённого плана с отмеченным одобрением сюжета.
Есть просмотр заданий/MP4 и отмена queued_local. Открытие/сохранение не запускает рендер.
Если плана нет, окно объясняет подготовку через агента и motion_director_plan_save.
Изолированная браузерная проверка с mock API подтвердила открытие, сохранение refs и новой ревизии,
блокировку запуска при несохранённых правках. Создание/изменение состава сегментов и selective cache ещё не реализованы в UI.

Ожидающее исполнение можно отменить POST `/api/studio/motion-director/scenes/{scene_id}/jobs/{motion_id}/cancel-waiting`
или MCP `motion_director_cancel_waiting`. Отмена допускается только в queued_local и только своей сцены;
захват задания диспетчером и отмена используют условный UPDATE, поэтому отменённое задание не отправляется.
Уже начатая передача возвращает 409; общая работа ComfyUI не прерывается.
При скачивании итоговый файл получает `output_sha256` в SQLite-квитанции. Endpoint file проверяет хеш;
подмена/редактирование скачанного MP4 возвращает 409 и требует отдельного QC изменённого файла.

Очередь показывает для Motion Director ID сцены и ревизию, объяснение состояния сверки и ссылку
на готовый MP4 с пометкой «требуется QC». Сводки и MCP-статусы исключают plan_json/graph_json/manifest_json,
чтобы polling не пересылал весь контекст модели; запрос заданий сцены фильтруется в SQLite.
Сырые снимки остаются в квитанции и не удаляются. Интерфейс редактора сегментов ещё не подключён.

`local_studio/motion_jobs.py` добавляет SQLite-квитанции исполнения в общую очередь (`motion_jobs`).
POST `/api/studio/motion-director/scenes/{scene_id}/execute` принимает сохранённую `expected_revision` и
`story_approved=true`; повтор той же ревизии возвращает прежнюю квитанцию. MCP: `motion_director_execute`,
`motion_director_jobs`. Снимок включает план и SHA-256 медиа. Перед отправкой медиа загружаются заново из библиотеки,
пути перепривязываются и граф сверяется с `/object_info`. Source Video для исполнения требует библиотечный `asset_id`.
Диспетчер соблюдает Pause/FIFO, при занятом ComfyUI подготовка ждёт; stage-loop H3 использует ту же блокировку.
Потеря ответа или прерывание в uploading переводит квитанцию на сверку метки `studio_motion_id` в queue/history,
без повторного POST /prompt. Готовый MP4 скачивается атомарно в results и остаётся связан с scene_id/revision;
GET `/api/studio/motion-director/jobs/{motion_id}/file` отдаёт результат. Техническое completed не означает приёмку QC.
Путь проверен на HTTP-макете: потеря ответа, восстановление без повторной генерации, ошибка исполнения и скачивание.
Совместимость на живом ComfyUI, UI карточки сегментов, сохранение отдельных сегментов/кэша и selective rerun ещё не подтверждены.

План сохраняется через GET/PUT `/api/scene-runs/{scene_id}/motion-plan` и MCP
`motion_director_plan_get` / `motion_director_plan_save` в `scene-runs/motion-plans/{scene_id}.json`.
Это подготовленный план, не активное GPU-задание: сохранение не запускает сборку сцены.
Создание требует `expected_revision=0`, изменение — текущую ревизию; устаревшая запись возвращает 409.
Отпечатки сегментов включают настройки, промпт, медиа и отпечаток предшественника при входящей непрерывности.
`invalidated_ids` показывает изменённые/зависимые сегменты; `removed_ids` — удалённые. Эти поля не доказывают наличие пригодного кэша.
MCP чата с `H3_SCENE_ID` запрещает читать и менять чужой план. Сохранение атомарно под общей блокировкой SceneRuns.
Путь и расширение загружаемых медиа разделены: библиотека хранит файлы под хешем, расширение берётся из original_name/MIME.

Передача медиа доступна агентам через `motion_director_upload_image` и `motion_director_upload_video`.
Видео загружается из библиотеки Studio в отдельный узел частями по 512 КиБ через его `/minimax/motion-director/upload_chunk`;
локальная временная копия и SHA-256 исключают смешивание изменяемого исходника. Ошибка подтверждения части останавливает передачу.
Возвращаемый `video_file` используется в `source_video`; произвольные пути на Mac не принимаются.
`motion_director_graph` собирает граф локально, `motion_director_preflight` сверяет его с `/object_info` без рендера.
Обе операции используют ту же схему сегментов, что `motion_director_compile`, с обязательным seed.
Проверка графа не подтверждает идентичность героев или присутствие медиа и не разрешает отправку автоматически.
Загрузка проверена HTTP-макетом; исполнение узла и сохранение результата в очереди Studio ещё не подключены.

Он регистрирует `MiniMaxH3MotionDirector` и при загрузке патчит внутренние части ComfyUI, поэтому требуется изолированная проверка версии ComfyUI и A/B на точном сервере до включения в основной рендер.

`scripts/install_h3_motion_director.sh --apply` устанавливает закреплённый коммит только при пустой очереди. Он не перезапускает ComfyUI и не запускает рендер. После отдельного перезапуска `--check` сверяет коммит и `/object_info`; тот же read-only контракт доступен через `/api/studio/motion-director` и агентам через универсальный `studio_api_get`. Отсутствие узла или несовпадение входов возвращает `api_compatible=false`; никаких молчаливых fallback в текущий граф нет.

У v1.2.0 Mixed Mode управляется `task_type=mixed` и `timeline_data` (JSON `version:1`, `timelineMode:mixed`, сегменты с mode/prompt/inputs/continuity); это машинный вход ComfyUI. `External Inputs` применимы к отдельным режимам, а не к Mixed v1. Selective Run требует проверки зависимостей и актуальности кэша следующих сегментов. До первого GPU-прогона нужны адаптер ассетов Studio→узел, проверка графа по живому `/object_info`, хранение версии каждого сегмента/кэша и проба MP4 со звуком. Настройки Turbo и 4 шага не становятся умолчанием; существующий BF16/24–25 шагов и принятый рецепт не меняются. Результат рендера не считается принятым без просмотра всего видео, стыков, персонажей и звука.

Подготовка контекста через подписку (29.10.2026): `context_ir_agent.py` собирает структурированный запрос по фото и выборкам видео, вызывает существующий `agent_tasks`/`agent_brain` и компилирует ответ прежними валидаторами Context-IR. `context_dispatch.py` обслуживает эту подготовку независимо от GPU; `dispatcher.py` больше не удерживает GPU-очередь на время ответа агента. Старые remote-wire запросы остаются на сверке через прежний API, новые помечаются backend=subscription_agent до CLI-вызова.

Постановка шота (добавлено 29.10.2026): `production-spec-editor.mjs/css` — отдельное окно правки существующего ShotSpec из карточки `storyboard.mjs`. Проверка идёт в `/api/production/spec/validate`, затем версия сохраняется на cut через `editCuts`/`saveDraft`. Модуль не отправляет рендер. `productionSpecChanged` отмечает уже готовый дубль как устаревший до новой генерации. Серверные контракты — `local_studio/production_spec.py`, компиляция в задание — `production_compile.py`; перечни режиссуры остаются в `app/director_schema.json`.

`production-beats-editor.mjs` отвечает за строки действий внутри этого окна: добавление/удаление, участников и причинные ссылки. Он возвращает описание родительскому редактору; сохранение/версии/API остаются в `production-spec-editor.mjs`. Удаление не может оставить шот пустым или разорвать ссылку реакции на причину.

`production-spec-model.mjs` создаёт незаполненный черновик постановки по подписанным фото героев. Кнопка «Создать постановку» работает и без ранее полученного от агента ShotSpec; неизвестная франшиза выбирается пользователем. Первый сохранённый контракт имеет revision=1. Действия, физические особенности и доказательства поведения автоматически не придумываются.

`production-behavior-editor.mjs` — редактирование паттернов героя и их источников внутри ShotSpec. `production-beats-editor.mjs` связывает записи с действиями. Удаление используемого паттерна блокируется; изменение содержания сбрасывает отметку проверки автором в draft. Реестр общий для одной постановки, отдельная глобальная база не создаётся.

Визуальная постановка: `app/visual_profiles.json` — четыре авторские адаптации методов с первичными источниками и явной пометкой «не проверено рендером»; `local_studio/visual_profiles.py` — read-only каталог API. `production-look-editor.mjs` выбирает метод и фото с ролью «Стиль» внутри ShotSpec. `production-frame.mjs` собирает запрос начального изображения с отдельными ролями героев/пространства/стиля; его используют `storyboard-model.mjs` и `scene-keyframe.mjs`. Общий профиль проходит через `production_compile.py` и в видео. Это не новая физическая модель камеры и не библиотека просмотренных кадров фильмов.

Как устроен проект и куда вносить правки руками. Обновлено 2026-10-15.

## Карта ответственности и навигация по коду

Новые вычисляемые правила принадлежат модели/контрактному модулю; `app.mjs` не должен становиться владельцем нового домена. Новую проводку главной страницы кладут в подходящий `app-*.mjs` или в новый модуль, а не в `app.mjs`.

## Правило комментариев

Комментировать инварианты и границы: почему draft блокируется при записи из другой вкладки, почему настройки шота временно подменяются и восстанавливаются, как роль референса превращается в граф. Очевидное действие кода не пересказывать. Новый блок в `app.mjs` должен иметь явного владельца состояния и модульную точку вынесения.

С 2026-10-28 `app.mjs` разрезан на части (было ~2750 строк). Правила частей:
- общие значения, которые пишут несколько частей (открытый проект, выбранный шот/результат, @-меню, доступность GPU), — в `app-state.mjs` как `appState.*`; значение, которое пишет одна часть, экспортирует она сама (`export let`, остальные только читают);
- обработчики событий части собраны в её `install*()`; `app.mjs` вызывает их в прежнем порядке, поэтому порядок подписок не изменился;
- модули `app-*` не импортируют `app.mjs` (иначе он выполнится второй раз), а при загрузке не вызывают друг друга — только объявляют функции.

Бэкенд Mac Studio (`local_studio/`, с 2026-10-28 так же разложен по частям):

| Файл | Что внутри |

## CREATE workspace

Главный экран Studio в `preview/h3-director/index.html` компонуется стилями
`create-workspace.css`; список 1–4 реальных заданий, независимые seed и обработчик
отправки находятся в `create-workspace.mjs`. Существующие reference uploader,
prompt mention, director settings, `enqueue()` и локальный job API остаются источниками
функциональности. Результаты в правой колонке строятся из завершённых заданий и
воспроизводятся через локальный `/api/jobs/{id}/video`; фиктивные превью не создаются.
CREATE хранит ID последней группы заданий локально и показывает только её варианты;
вся история доступна через очередь.
Остальные настройки раскрываются через `#createControls`. Экран сцены открывает этот
же блок для существующих режиссёрских параметров.

Три основных раздела используют одну навигацию: Create `/`, Story `/?view=scenes`,
Assets `/?view=assets`. `assets-workspace.mjs/css` показывает существующую
медиатеку как самостоятельный экран; из Create она остаётся окном выбора референсов.
Вкладка готовых видео читает завершённые задания из `/api/jobs` и открывает их MP4,
добавление в сюжет без повторной загрузки файла.
`studio-product.css` задаёт общую иерархию Create, Story и Assets; `story-handoff.mjs` связывает готовый
job с дублем шота. «Монтаж» (`/editor/`) — таймлайн поверх того же монтажного листа (EDL): всё, что настроено на странице, попадает в MP4.
`film-assembly.mjs` проверяет все сцены и выбранные дубли перед сборкой полного фильма;
он использует существующий `/api/storyboard/concat` с ограничением 60 шотов и сохраняет
результат в черновике проекта как `filmAssembly`.
Общие решения по интерфейсу описаны в корневом `DESIGN.md`.

### Привязка референсов к герою

Библиотека показывает сверху разделы франшиз пользователя;
файлы на разборе остаются в хранилище и загрузках, но не показываются в разделах;
внутри раздела группирует лицо, тело, костюмы, квартиру/локации и видео. Источник
принадлежности к франшизе — карточки персонажей и локаций `/api/franchises/*/entities`;
один `asset_id` может принадлежать нескольким франшизам. Известные файлы без карточки
не относятся ни к одной франшизе по догадке. Библиотека хранит в `project.library[asset_id]` явные поля `franchise`, `characterName`, `look`
и `preferredRole`. Они организуют карточки «франшиза → персонаж → образ/одежда» без переноса
или удаления исходных файлов. Кнопка «Добавить образ в сцену» выбирает только фото
лица/тела данного героя и костюм выбранного образа; при нескольких фото одной роли
требует ручного выбора. В `project.references` у прикреплённых файлов записываются
`owner=characterName` и роль, после чего действует приведённая ниже проверка Mac/GPU.
Перед постановкой задания именованная просьба «замени ... на ALEX»
подбирает портрет из картотеки; слова «Хэллоуин», «Рождество», «Супергерой»
требуют отдельного костюма этого же героя. Если имя встречается в нескольких
франшизах, костюм не найден или остался только одетый снимок без портрета,
задание отклоняется с конкретным объяснением до очереди GPU. Новые образы требуют визуальной проверки готового видео.
Поля библиотеки сами по себе не меняют существующие задания и не доказывают качество
получившегося видео; плохо названные и неразмеченные файлы нельзя назначать по догадке.

`<Picture N>` обозначает порядок изображения во входах `ref_images.ref_image_N`, а не тип объекта.
Роль и владелец сохраняются в манифесте задания вместе с `asset_id` и SHA-256; Mac и GPU
проверяют порядок и содержимое файлов. У фото лица и костюма одного героя одинаковый владелец,
а официальный H3-промпт собирает их внутри одного `<Subject N>`. При нескольких героях костюм,
видео актёрской игры и голос без владельца отклоняются до очереди. У видео и аудио владелец
передаётся в GPU-манифесте и в задании Qwen Director. Перед рендером Mac и GPU сверяют
`subject_definitions` с владельцами и исходными метками официального промпта.

`MiniMaxH3ReferenceToVideo` не имеет отдельных входов «лицо», «костюм» или «предмет»:
все изображения поступают в нативный `ref_images` по порядку, а семантика их использования
задаётся структурированным промптом. Поэтому эта проверка гарантирует согласованность
контракта и графа, но не гарантирует визуальное сохранение идентичности без рендера и оценки.

Если официальный промпт правильно называет героя, но пропускает один из уже назначенных ему
источников в `subject_definitions`, Mac Studio добавляет только отсутствующую метку с её ролью;
чужие метки и перепутанные владельцы остаются ошибкой. Для видео с несколькими исполнителями
Studio показывает «Связать героев» и отправляет `reference_performers` в Mac API. Явные строки
`REFERENCE PERFORMER A → ALEX` / `B → NOVA` могут заполнить пары из текста; если соответствие
неоднозначно, пользователь выбирает его в диалоге до отправки задания.

Для нескольких говорящих героев Studio хранит настройки голоса отдельно по имени. Шаблоны школ и жанров задают инструкции H3, а не запускают отдельную модель актёра или синтеза речи. Аудиообразец служит референсом; точное совпадение голоса и интонаций требует проверки готового MP4.

## Как добавить поле или вариант

1. Правишь **только** `app/director_schema.json` (`key`, `type`, `options`, подписи `label.ru` / `label.en`).
   Значения `value` — английские, они уходят на сервер и в промпт.
   `"prompt": false` — поле управляет узлом и не пишется в текст промпта (пример: `color.grade_strength`).
2. `bash scripts/check.sh` — проверит, что все встроенные пресеты проходят серверную валидацию.
3. Перезапусти Mac Studio. Если поле нужно на GPU — задеплой `app/` на сервер.

Compute backend живёт в `local_studio/compute/`: `vast.py` — ограниченный REST-клиент, `keychain.py`/`keychain.swift` — macOS Keychain, `manager.py` — SQLite-журнал и подтверждаемые операции, `router.py` — API с Origin-проверкой для всех изменяющих запросов. `operator.py` добавляет `/api/compute/operator/plan`, `/operations`, `/run` и WebSocket `/terminal`. План читает Keychain, R2 LATEST и состояние выбранного сервера; действия ограничены существующими `verify_h3_server.sh`, `h3_server_drift.sh`, `h3_up.sh`, `h3_new_server.sh`. Терминал выполняет SSH от локального пользователя Mac; доступен только с localhost страницы Studio. Это интерфейс и воспроизводимый runbook поверх имеющихся скриптов, без установленного Terraform или Ansible.

Основные пути: `POST /api/compute/provider-key` проверяет ключ перед Keychain; `GET /api/compute/status` возвращает баланс и endpoint туннеля; `GET /api/compute/offers` отбирает on-demand NVIDIA конфигурации; `POST /api/compute/rent` повторно проверяет цену и характеристики перед арендой; `POST /api/compute/instances/{id}/deploy` запускает существующий `infra/h3_up.sh`; операции можно читать через `GET /api/compute/operations/{id}`. Остановить текущий сервер можно явным действием при пустой очереди; удалить его — только после статуса `stopped`; повторно развернуть поверх него нельзя. Остановленный сервер продолжает тарифицировать диск; уничтожение Vast необратимо. Никакого auto-stop нет.

### Scenes: фактическая цепочка

`Идея` и цель 30–90 с → Mac `POST /api/scene-plans` → агент Studio (`local_studio/agent_tasks.py`, правила `app/scene_planner.py`)
(структурированный JSON, 4–12 шотов по 4–15 с, проверка общей длительности и максимум трёх
продолжений подряд) → предпросмотр плана и локальные рекомендации по крупности/темпу/связям →
утверждение → `project.cuts` и `project.sceneDirector` в черновике → подбор/генерация ключевых
кадров → существующая последовательная очередь H3 → QC каждого готового шота → склейка или
раздельные клипы в монтаже.

Планирование не ставит рендер в очередь. При недоступном GPU интерфейс показывает ошибку, не
подменяет Qwen шаблонным «AI-планом». Генерация кадров Qwen Image Edit требует исходное фото
и подтверждённую capability; Qwen Image 2.1 не используется по умолчанию из-за некоммерческой
лицензии. Готовый шот проверяет агент по кнопке «◇ Проверить» (`job_frames`); автоматической
проверки и автоматической перегенерации шота нет. Для полной проверки
референсов нужны следующие изменения и реальный GPU-тест. Несколько пробных дублей на шот и полная
схема `Project → Sequence → Scene → Shot → Take` ещё не подключены; текущая очередь H3 даёт
один актуальный `shotJobId` на шот и сохраняет старые ролики в истории.

Страница «Звук и речь» сохраняет черновик через `local_studio/audio_project.py`. Отдельная очередь в `local_studio/audio_jobs.py` отправляет готовый проект в `app/audio_jobs.py`, если необходимые возможности установлены. `app/audio_mix.py` сводит дорожки через FFmpeg; оригинальный звук возвращается отдельным WAV. Синтез речи подключается через изолированный `app/audio_cosyvoice_line.py`, создание музыки через изолированный `app/audio_acestep_music.py`. ### Подготовка входов: участки и повторное использование (2026-10-09)

Автономный Create принимает `reference_windows` по ID прикреплённых видео.
ProductionQueue подготавливает участок до снимка Context-IR через общий
`reference_segments.py`; в snapshot и H3 manifest попадает ID участка с исходными
ролями/владельцами/номерами. Рецепт сохраняет исходный ID, диапазон, ID и SHA результата.
Несовпадение длительности, неизвестный референс и окна для edit-рецепта отклоняются.
Для обычных запросов сохранён прежний request_hash, включая повтор после обновления.

Сегменты используют межпроцессную блокировку, SHA исходника и кэша, атомарное
размещение MP4. Исходные материалы не перезаписываются. Повреждённый зарегистрированный
участок отклоняется, не выдаётся за готовый. Формат участка: H.264, 24 fps, AAC при
наличии звука; это повторное кодирование, не без потерь.

`reference_preparation.py` хранит JPEG/кадры для Qwen в `reference-previews/` внутри
Studio data. Ключ: SHA исходника, тип, длительность, версия извлечения. Владельцы,
роли и инструкции остаются в snapshot; этот кэш не подменяет семантический анализ.
Кэш Context-IR по fingerprint модели/схемы и полному контексту остаётся отдельным.
При изменении масштаба/позиции кадров/кодирования требуется поднять VERSION.

Отмена production с Context-IR uploading/running/needs_reconciliation сохраняет
квитанцию и ожидает завершения/сверки; новых генераций не создаёт.

### Фактическая телеметрия FirstBlockCache (2026-10-09)

`install_cache_metrics.py` инструментирует только nodes.py с проверенным SHA
из pinned FBCache f7a2712. Идемпотентная вставка не меняет решений decide(),
параметров, входов узла или графа. Upstream MIT attribution остаётся в пакете.
`app/comfy_nodes/h3_cache_metrics/runtime.py` сохраняет отчёт до reset():
full/reused forward calls, номера повторных вызовов, residual/temporal min/max,
фактический config и wall time обёртки sampler. Это не measured speedup и не
доказательство качества лица; вызовы модели не обязательно равны sampler steps.

ExecutionContext задаёт prompt_id и sampler node_id. Отчёты нескольких проходов
не перезаписываются, сохраняются атомарно под output/.h3-cache-metrics/UUID.json.
Comfy `/h3/cache-metrics/{UUID}` → ComfyClient.cache_metrics → GPU job status
cache_runtime → Mac worker → director.cache_execution.runtime_counters → job-feed.
Валидация проверяет совпадение ID и счётчики. Отсутствие расширения/отчёта не
подменяется нулём и не ломает загрузку MP4. Ошибка записи метрик не меняет inference.
A/B runner сохраняет telemetry вместе с фактическими timings для будущего сравнения.
Установщик и overlay bundle включают runtime и patcher. GPU здесь не обновлялся.

### Общие отпечатки входов

`app/fingerprints.py:json_sha256` задаёт единый формат JSON → SHA-256 для Context-IR
(старый импорт `schema.digest` сохранён), ProductionSpec, отчёта воспроизводимости и
цепочки сегментов Motion Director. Для конечных JSON-значений формат сохраняет
существующие отпечатки; NaN/Infinity отклоняются. Отпечаток доказывает совпадение
описания входов, но не наличие GPU-кэша или одинаковый результат генерации.
Остальные исторические форматы хеширования пока не мигрированы: их изменение
требует проверки хранимых квитанций и кэша.

### Допуск дубля к склейке

`local_studio/take_acceptance.py:take_is_accepted` — общая проверка для
`SceneRuns._glue` и `/api/storyboard/concat`: QC относится к текущему job ID,
выбран тот же дубль, постановка не помечена изменённой, последняя проверка не
отклонена/устарела. Legacy-шот без `selectedTakeId` проверяется по `shotJobId`.
Это допуск по сохранённым данным сцены; он не доказывает просмотр MP4, целостность
его байтов или совпадение незаписанной ревизии. Эти доказательства остаются за
квитанцией результата и производственной приёмкой; объединение их маршрутов ещё
предстоит выполнить.

Уточнение допуска дублей: непустой `takeReview` разрешает монтаж только при
`state=accepted` и совпадающем job ID. Запущенный повторный review блокирует старый QC.
Автоматический review получает снимок постановки/промпта/референсов; изменение
снимка до получения ответа переводит verdict в stale и оставляет сцену ожидающей.
Перед FFmpeg `shot_paths` вызывает общий `production_review.output_digest` и
проверяет сохранённый SHA-256 результата. Хеширование вынесено из event loop.
Legacy-результат без записанного хеша остаётся без доказательства прежней
целостности; это не равно подтверждению воспроизводимости. Файл всё ещё может
быть изменён внешним процессом после проверки: неизменяемое хранилище результатов
или закреплённый снимок входов монтажа пока не реализованы.

Общий допуск дубля используется также в `studio_readiness`; JS `acceptedShot`
повторяет этот контракт для планировщика, обзора и сборки фильма. Одинаковые
случаи проверяются между Node и Python. Ручное решение `manual_review` при
`shotQcReview=accepted` допускается как явное решение пользователя; само по себе
оно не доказывает полный просмотр. Продолжение видео требует полного того же
допуска: один лишь `decision=accept` без состояния accepted больше не достаточен.

### Единая приёмка результатов генерации и монтажа

`production_artifacts.py` разрешает ссылку `{kind: job|concat|edl, id}` в
существующую квитанцию и MP4. Файлы и задания не копируются. EDL допускается
только при `state=completed` и явном `draft=false`; идентификаторы монтажа —
32 hex-символа, путь MP4 определяется хранилищем, а не вводом клиента.
`production_review.py` применяет один порядок технической и творческой приёмки
ко всем видам результата. Журналы разных видов изолированы, legacy-job API и
его прежние файлы сохранены; оба job API синхронизируются по одному lock.

GET/POST `/api/production/artifacts/{kind}/{id}/reviews` читает текущий хеш и
записывает реальный отчёт проверяющего. MCP `production_review_record` принимает
`artifact_kind` (по умолчанию job), ID результата передаётся в прежнем `job_id`.
`run_done` для фильма принимает `final_artifact={kind,id}` или legacy
`final_job_id`, требует действующую творческую приёмку этого MP4 и сохраняет ID
приёмки. Указывать оба вида ссылки одновременно нельзя.

`viewed_ranges`, `audio_reviewed` и `evidence` — отчёт проверяющего, не
автоматическое доказательство просмотра. Система не заполняет их за пользователя
или агента. Изменённый MP4 теряет прежнюю приёмку по хешу. Старые монтажные
квитанции без исходного output_sha256 не доказывают неизменность с момента
экспорта; приёмка относится к точным байтам просмотренного файла.

### Версия входов монтажного результата

`assembly_receipt.py` — один снимок для склейки сцены и EDL: точный рецепт,
SHA-256 всех файлов (`sources`) и общий `input_fingerprint_sha256`. Пути хранения
не входят в версию содержимого. Склейка хранит снимок в своей `.json`; EDL —
в `.json` рядом с фактической командой FFmpeg. Чистовой/draft режим входит в
рецепт EDL. SHA-256 готового MP4 хранится в квитанции результата и проверяется
общей приёмкой. EDL сверяет исходные job MP4 с сохранёнными хешами завершения.
Сверка исходников до/после выполнения не позволяет объявить готовой сборку при
обнаруженном изменении файла; это контроль дрейфа, не неизменяемая копия источников.
Повтор всё ещё требует доступности тех же байтов источников, зависимостей,
шрифтов/графики и совместимой версии FFmpeg. Совпадение входного хеша не обещает
побитового совпадения экспорта на другой машине.

### Единый обзор сохранённого производства

`GET /api/draft/production?franchise_id=…` / MCP `studio_production_state` строят
общую проекцию поверх существующих владельцев данных: одна ревизия черновика,
готовность сцен, текущие и исторические дубли, состояния заданий и записанные
хеши MP4. MCP задачи ограничивает результат своей франшизой. Проекция не создаёт
вторую базу, не запускает GPU и явно сообщает, что байты файлов ею не проверены.

`scene_versions.py` фиксирует при запуске `definition_snapshot` — порядок и
авторские поля шотов. `studio_readiness` сравнивает его с сохранённой сценой;
расхождение блокирует завершение задачи через orchestrator. Старые сборки без
снимка сравниваются с текущим содержимым своего журнала с пометкой legacy_run.
Версия этого снимка покрывает последовательность шотов, а не все настройки,
референсы и окружение inference. Уже исполняемая сборка автоматически не
отменяется и не пересоздаётся при изменении холста.

Новые запуски холста передают `source_context` с сохранёнными `sceneStyle`,
`seed`, `renderState`, `referenceState`. `context_snapshot` в журнале сборки
фиксирует их содержимое и SHA-256. Readiness и общий production-state сообщают
`context_version`; изменение этих входов блокирует завершение задачи по старой
сборке. Отсутствующий снимок старой сборки даёт `matches=null`, `unknown_legacy`,
а не положительную проверку. Это версия назначений и настроек на холсте;
физические хеши медиа, граф, веса и среда хранятся/проверяются отдельно по
квитанциям реально выполненных заданий. Передаётся только контекст, без второй
копии всех шотов и исторических дублей.

Ручная приёмка текущего дубля сохраняет прежний `takeReview` в истории и
записывает новое явное решение `reviewer_reported`; callback старой проверки
применяется только при совпадении её ключа. API отвергает приёмку чужого job ID.
Кнопка холста и журнал сборки используют одинаковое новое решение.

`worker.py` сверяет базовый BF16-профиль, если GPU API объявил
`render_profiles_v1`. Явное отсутствие весов отклоняется до POST задания.
Для старого API без этой возможности прежняя совместимость сохранена;
экспериментальные профили по-прежнему требуют соответствующую capability.

### Наблюдение выполненного графа

`app/execution_evidence.py` извлекает `execution_observation` из истории ComfyUI
только при совпадающем prompt ID: хеш графа из history, типы узлов, статус и
серверные отметки времени. `ComfyClient` по завершении один раз запрашивает
`system_stats` и сохраняет доступные os/python/pytorch/comfyui версии. Аргументы
процесса не сохраняются. Отказ stats не теряет готовый результат. Наблюдения
кэшируются ограниченно (200 заданий); worker записывает их в SQLite до скачивания,
а reproducibility отдаёт рядом с прежним `execution_record=graph_prepared`.

Это наблюдение истории и runtime в момент опроса, не подтверждение фактически
загруженных весов или commit каждого custom node: `weights_sha256` и
`custom_node_versions` остаются null. Хеш из history — точный JSON; прежний хеш
подготовленного графа нормализован другим форматом, напрямую их не сравнивать.
Существующие графы и защищённые рецепты не изменены. На живом GPU этот новый
паспорт ещё не проверен; пройдены HTTP-макет, сохранение/повторное чтение SQLite
и тесты существующей очереди.

### Браузерная проверка ручного review

На отдельном uvicorn с временной базой, без GPU URL, создан синтетический
4-секундный клип со звуком и намеренно отклонённый дубль. Playwright выявил,
что новый canvas inspector не показывал ручные решения и что нажатие до первого
polling tick сохраняло решение только в draft. Исправлено: canvas делегирует
`qc-accept/qc-reject` прежнему storyboard; `tellRun` при необходимости читает
журнал перед PATCH без зеркалирования старого вердикта поверх нового решения.
Смена сцены во время чтения отклоняет запись.

В браузере проверено: нажатие «Принять после просмотра» → draft=accepted,
server takeReview=accepted, старый rejected в истории; после reload нажатие
«Отклонить дубль» → draft/server=rejected. Проверка состояния выполнена после
очередного polling tick. Пройдены 43 целевых JS-теста и syntax checks обоих
модулей. Изолированный сервер остановлен, временная база удалена. Это проверка
UI и сохранения решения на синтетике, не художественная приёмка фильма и не
доказательство полного просмотра пользовательского MP4.

### Motion Director и импортированные финалы в общей приёмке

Виды `motion` и `asset` включены в тот же ArtifactReference, API/MCP приёмки и
`run_done.final_artifact`. Motion читается из существующей таблицы `motion_jobs`
без создания нового задания; завершённое видео ассета — из существующей
библиотеки. В обоих случаях проверяются разрешённое хранилище и записанный
SHA-256. Журналы приёмки разделены по виду, одинаковый ID не переносит приёмку
между результатами. Импорт видео сам по себе не означает приёмку фильма.

`production_state` читает `motion_results` каждой сцены из прежней SQLite:
ревизию, статус, remote ID и хеш результата. Motion download записывает
`execution_observation` в metrics_json тем же `history_evidence`, что H3.
Снимок runtime там отсутствует, если его не наблюдали; сохранение истории не
означает проверку весов. Пройдены 79 целевых тестов (Motion/приёмка/общий
обзор/оркестратор/MCP) без GPU, включая изменение принятых байтов.

### Индекс проверенных файлов весов

`app/model_inventory.py` и `scripts/h3_attest_weights.py` проверяют явно
перечисленные в weights.tsv файлы по SHA-256 и атомарно записывают индекс.
Пример однократной проверки (не запускать на каждом задании):

```sh
python3 scripts/h3_attest_weights.py --root /workspace/h3 --weights-tsv /tmp/h3-weights.tsv --out /workspace/h3/verified-weights.json
```

`check_weight` затем сравнивает размер, inode, device, mtime_ns, ctime_ns и
разрешённый symlink target. Изменение/отсутствие файла делает прежний хеш
непригодным; отсутствие строки или неизвестная версия индекса дают unknown.
Повторное чтение больших весов на быстрой проверке не выполняется. Тест
подтвердил отказ даже при восстановлении исходного mtime после изменения байтов.

Это доказательство файлов на диске в момент attestation и последующая проверка
их метаданных, не криптографическая гарантия неизменности без повторного чтения
и не доказательство загруженных в VRAM тензоров. CLI не устанавливает файлы,
не перезапускает сервисы и не запускает inference. Подключение индекса к
наблюдению ComfyUI ещё не выполнено; на GPU индекс в этом этапе не создавался.

### Контракт внешности при замене — все франшизы

`character_identity.py:replacement_identity` используется обоими компиляторами:
`source_swap_identity_contract` и Character Swap. Источник лица — собственный
портрет, иначе собственный full-body; тело и пропорции — собственный full-body;
одежда — явно назначенный костюм, иначе full-body. Карта другого героя не может
стать источником этих признаков. Отсутствующий full-body вызывает отказ до очереди
полной замены. Чисто фотографический путь не меняется.

Источник видео переносит исполнение, а не массу тела, head/body ratio, длину
конечностей, расположение глаз или костюм исходного исполнителя. Поза и контакты
должны быть адаптированы к анатомии целевого героя; относительный масштаб — по
целевым героям, а не по исходному составу. Никакие числовые пропорции по тексту
имени/франшизы не придумываются. `PROPORTION_QC` добавлен в проверку дублей с
требованием отличать перспективу от деформации и отмечать невидимые/неподтверждённые
признаки как unverified.

Это контракт компиляции и критерии проверки, а не новый geometry-control узел,
не автоматическое измерение морфометрии и не доказательство выполнения моделью.
Нового MP4 в этом этапе нет; до включения рецепта как проверенного требуется
целевая проба и полный AV-QC. 55 целевых проверок прошли, включая прежний
фотографический рецепт и правильное раздельное назначение лица/тела/костюма.

### Карта внешности в Motion Director

Для `source_video` с identity pictures сегмент теперь требует `replacements`:
`owner`, `performer`, `body_asset_id`; необязательные `face_asset_id` и
`costume_asset_id`. Все ID обязаны быть в pictures данного сегмента. Один
исполнитель/владелец/полный образ не назначаются двум героям; перекрёстное
использование референса разных владельцев отклоняется до графа. Общая
`replacement_identity` компилирует эти роли в реальный prompt сегмента.
Редактор сохраняет карту при правке/перестановке сегментов; MCP compile schema
описывает её явно. Карта входит в отпечаток сегмента.

Старые source-video планы с анонимными identity pictures требуют явного
назначения карты перед новой компиляцией/запуском. Их задания и MP4 не удаляются
и автоматически не повторяются. Source-video без картинок остаётся отдельным
путём обработки исходника без заявления о замене героя. Проверка карты не
доказывает визуально, что файл действительно изображает нужное полное тело:
референсы всё ещё нужно осмотреть, а пропорции проверить на полном результате.
Пройдены 102 Python и 5 JS-проверок; нового GPU-результата нет.

### Подключение индекса весов к контексту ComfyUI

Отдельный custom-node пакет `h3-execution-context` (без новых узлов графа)
подключается установщиком overlay рядом с прежним Studio bridge. Его on-prompt
observer сохраняет sidecar в `output/.h3-execution-context/<prompt_id>.json`;
GET `/h3/studio/execution/{prompt_id}` читает его по canonical UUID.
Пакет использует отдельную устанавливаемую копию model_inventory, не требует
импорта GPU API в процесс ComfyUI. Установщик в этой работе не запускался.

На получении prompt записываются точный graph SHA, runtime Python/PyTorch,
хеши code objects методов загруженных классов и доступные статусы весов из
`<H3_ROOT>/verified-weights.json`. Крупные веса в on-prompt не читаются.
Неизвестный loader selector, неоднозначный путь, отсутствующий индекс или
изменённый файл не получают подтверждённого SHA. Индекс не создаётся автоматически.

H3 ComfyClient и MotionQueue после завершения читают sidecar. Общий
`merge_prompt_context` включает его в execution_observation только при совпадении
prompt ID, raw graph SHA, версии и стадии. Несовпадение явно отмечается;
недоступный модуль не теряет готовый MP4. Контекст prompt_received не является
подтверждением принятия/исполнения: это устанавливается отдельно историей.

Предел: диск и загруженные методы класса не описывают все зависимости/closures,
состояние GPU-кэша и VRAM-тензоры. `environment_complete=false` сохранён намеренно.
На временном каталоге проверены установленная структура пакета, импорт локальной
inventory-копии, запись sidecar без изменения графа, совпадение/отказ привязки и
дрейф файлов. 42 целевых теста прошли; реальная установка/инференс не проверены.

### Ручное отклонение дубля и запоздалый QC

PATCH `scene-runs/{scene}/cuts/{cut}` обрабатывает ручное отклонение так же,
как принятие: текущая takeReview уходит в takeReviewHistory, новая запись
привязана к job_id и не содержит ключа старого callback. Для отклонения клиент
обязан прислать shotQc.job_id текущего дубля; устаревший/неуказанный ID получает
422. Сервер останавливает сборку без автоматического запуска нового дубля.
Кнопка «Отклонить дубль» отправляет ту же привязку и сохраняет решение в черновике.
Регрессия воспроизводит обе последовательности: ручной вердикт → противоположный
запоздалый callback, включая отклонение во время работающей сборки.

VideoReward, дополнительные depth-модели и Wan остаются исследовательскими
кандидатами, а не скрытыми обязательными зависимостями действующего H3-пути.

### Переносимый контракт Studio ↔ ComfyUI

`app/studio_extensions.py` задаёт один список исходных/установленных файлов
bridge и execution-context observer. `scripts/install_h3_studio_extensions.py`
используется общим GPU overlay и отдельно на CPU-стенде: по умолчанию сверка,
`--apply` — атомарная замена файлов с backup, без рестарта и загрузки моделей.
Сохранённые графы, edited-варианты и пользовательские файлы не удаляются.
`--url` отличает установленные файлы от действительно загруженных маршрутов.
`verify_h3_server.sh` проверяет тот же файловый/runtime контракт.
Bundle включает сам установщик и h3_attest_weights.py, поэтому для этого
этапа не требуется исходный Mac checkout или ручное копирование Python-модулей.

`scripts/verify_studio_engine.py` проверяет связку до GPU: общая версия API и
Director schema, три read-only маршрута bridge/observer, пять золотых графов,
61 существующая комбинация build_prompt и GraphPlan Motion Director против
реального object_info. В отчёте явно configuration_only/submitted=false/
inference_verified=false. Обработчики и все 69 проверок подтверждены на h3-local.
Исследовательские A/B-комбинации входят в матрицу совместимости графа,
но не становятся умолчаниями и не обещают художественное качество.

Ранее записанное ожидание живого GPU относится к последующему inference/QC,
а не к завершению разработки переносимого ядра: пользователь это уточнил.

### Готовый промпт агента → H3 без второго планировщика

Новые задания холста получают `settings.agent_prepared_prompt=true` из
`app-generation.mjs`. Store сохраняет этот признак вместе с заданием, worker
отправляет `precompiled_prompt=true`, `emotional_direction=false` независимо
от старого флага эмоциональной режиссуры. GPU API тогда пропускает LocalQwenDirector,
но оставляет обязательный `CLIPLoader` Qwen3-VL-32B для кодирования текста внутри
самой H3. Старые сохранённые задания без нового признака используют прежний путь;
утверждённый рецепт «только фото» и его граф не меняются.
