# H3: повторяемое быстрое развёртывание

## Текущий снимок R2 (2026-10-29)

Активный снимок Cloudflare R2: `h3-studio/snapshots/20261029-1340-422c75c`; это файловый архив софта/конфигов и манифест весов, не образ виртуальной машины Vast. `software.tar.zst` — около 18,2 ГБ, SHA-256 `0c904c5a436d41a16c1e31788fbd194339d5cffaed9405c02fa40198acbdc4ea`. Архив текущего GPU-кода/конфигов переиспользован из успешно выгруженного staging-снимка; новый полный archive/weight upload не делался. Манифест содержит 106 файлов; все их content-addressed SHA уже существуют в R2. Qwen Director 8B исключён из манифеста, обязательный H3 encoder `Qwen3-VL-32B` оставлен. R2 `LATEST`, SHA-маркер, отсутствие 8B и наличие 32B encoder проверены. Набор кода сервера соответствует `422c75c`; при восстановлении `h3_up.sh` дополнительно накладывает deployment-код текущего HEAD. При упаковке не запускались GPU-хеширование и рендер; предшествующая `verify_h3_server.sh` завершилась «ИТОГ: всё OK». В архив не входят задания, входы/результаты видео и `api-data`.

Для быстрого H3-развёртывания используй этот снимок и **не устанавливай LTX или Qwen Director 8B**. H3 text encoder `Qwen3-VL-32B` обязателен и остаётся. Подготовка промптов выполняется подписочным агентом; готовый Studio prompt отправляется как `precompiled_prompt=true` без повторной обработки перед H3.

`infra/h3_up.sh` использует выбранный stamp как базу, затем устанавливает код/конфигурацию из текущего HEAD через `scripts/h3_new_server.sh`; перед стартом убедись, что нужные правки уже в HEAD. Прочитать `docs/STATE.md`, `docs/DECISIONS.md`, `docs/TOOLS.md`, открытые пункты `docs/JOURNAL.md` и свежий `git log`. Серверный адрес брать только из запроса пользователя или свежего ответа Studio/compute provider, не из этого навыка или старого handoff.

Снимок рассчитан на RTX PRO 6000 Blackwell (97 887 МиБ), одну GPU с ≥94 ГБ VRAM и CUDA ≥12.8. Для запаса бери диск от 600 ГБ. Последнее восстановление предыдущего снимка заняло 19 минут; для нового хоста ожидать порядка 10–20 минут и сообщать фактический ход, не обещать мгновенный запуск. После overlay проверить Mac Studio, туннели `18188/18189/18191`, `/object_info`, текущие API. Для пути настроек использовать `docs/reference/STUDIO_STRUCTURE.md` и схему Studio settings → store → worker → API capabilities/required_nodes → graph из `AGENTS.md`.

Перед переключением проверить действительную Mac/GPU очередь и живой рендер. Состояние SQLite `running` само по себе не доказывает работу GPU; сверять remote job, серверную очередь и MP4. Не повторять задание автоматически и не выключать работающий рендер. Установщик должен пройти `scripts/check.sh`, сверку дрейфа (если старый сервер доступен), SHA всех весов и `scripts/verify_h3_server.sh` с `ИТОГ: всё OK`. После этого отдельно проверить доступность Studio и поддерживаемые функции; короткий MP4 делать только если пользователь поручил генерацию. Техническая проверка графа не является визуальной приёмкой видео.

При изменениях в deployment-путях `infra/h3_up.sh` запускает HEAD во временном detached worktree и передаёт endpoint, stamp и флаги; несвязанные файлы остаются в checkout. Если необходимые изменения уже в HEAD — продолжать. Если важная правка только в dirty deployment-файле, назвать её и не коммитить чужую работу. Не объявлять незакоммиченную правку развернутой.

Рабочий проект: корень этого репозитория, ветка `master`.
Навык запускает существующие установщики; не переписывает приложение и не создаёт свои тесты.
Один запрос пользователя «разверни сервер»/«восстанови» достаточен для выполнения согласованной установки, если endpoint и доступ уже есть. Не арендовать GPU без отдельного запроса и не запускать платный тестовый ролик без поручения.

## Одна команда для нового пустого сервера (режим пользователя: без LTX)

Из корня проекта:

```bash
mkdir -p logs
bash -o pipefail -c 'bash infra/h3_up.sh --host root@HOST --port PORT --stamp LATEST 2>&1 | tee "logs/deploy-$(date +%F-%H%M).log"'
```

Перед запуском сверить R2 `snapshots/LATEST`, `software.sha256` и `weights.tsv`. Последний проверенный stamp — `20261029-1340-422c75c`; всё равно читать живой LATEST и проверять SHA, отсутствие Qwen Director 8B и наличие манифеста. Если LATEST пустой/битый — взять самый новый завершённый stamp с архивом, SHA и манифестом; не угадывать по папке и не продолжать без манифеста.

По SSH проверь `nvidia-smi`, свободное место через `df -h` и состояние `/workspace/h3`: для нового сервера путь должен отсутствовать или быть пустым. Если там уже есть файлы, продолжать только когда `.h3-image-stamp` точно совпадает с выбранным снимком; иначе остановиться и выяснить, какой сервер/маршрут нужен. Не считать сервер пустым только по статусу compute API.

Подставить актуальные `HOST` и `PORT`: использовать endpoint, который дал пользователь, либо единственный новый/пустой GPU из свежего `GET http://127.0.0.1:18187/api/compute/instances` (`ssh_host`, `ssh_port`). Не восстанавливать поверх работающего сервера с непустым `/workspace/h3`; если нового target нет, задать один вопрос: «Пришлите `host:port` нового GPU и подключите к нему SSH-доступ». При нескольких кандидатах уточнить адрес. Не использовать IP из STATE/навыка как текущий.

Для Vast брать SSH-порт из `Open Ports: PUBLIC_IP:PORT → 22/tcp` либо из явной SSH-команды провайдера. `Machine Copy Port` — отдельное поле и не является SSH-портом. На новом endpoint `h3_up.sh` может сразу упасть с `Host key verification failed`, потому что его SSH работает без интерактивного подтверждения. Если запись для точного `[HOST]:PORT` отсутствует в `known_hosts`, выполнить однократное подключение своим SSH-ключом с `StrictHostKeyChecking=accept-new` и `BatchMode=yes`, затем повторить ту же команду развёртывания. При несовпадении уже сохранённого ключа не заменять его автоматически: выяснить причину смены ключа. Не переносить ключ со старого порта или другого сервера.

Проверить наличие Keychain-ключей R2 (`h3-r2-account-id`, `h3-r2-access-key-id`, `h3-r2-secret-access-key`), HF-токена (`h3-hf-token`) и SSH-ключа из `SSH_KEY=` в установленном `tunnel.sh`. Текущий `h3_up.sh` требует доступ к SSH, R2 и приватный HF token; проверять только наличие, значения не выводить. Если чего-то нет — одним сообщением назвать недостающие элементы и попросить настроить их локально в Keychain/SSH. Не просить токены, пароли или приватные ключи в чате. Если endpoint и доступы действуют, коротко проверить SSH, GPU, CUDA, диск, очередь старого сервера и пустоту target, затем сразу запускать restore.

LTX не добавлять и не скачивать в обычном восстановлении этой конфигурации. Установку LTX проводить только отдельной явной просьбой пользователя; она не является условием готовности H3.

## Источники и скорость

- Софт/venv/ComfyUI/узлы и дополнения: Cloudflare R2, `h3-studio/snapshots/`. Использовать `LATEST`; при отсутствии или пустом ответе брать самый новый завершённый снимок с `software.sha256`, а не объявлять бакет пустым. `rclone cat` отсутствующего объекта иногда возвращает 0 и пустой текст.
- Основные H3 BF16, Qwen encoder и VAE: авторизованный HF, по маршруту существующего `h3_up.sh`. LoRA, 3D/стили/бой/лицо, LivePortrait, звук, SeedVR2/RIFE и остальные файлы описи — R2. Ничего из описи не пропускать молча. Явный выбор источника пользователем имеет приоритет.
- LTX-2.5, Gemma, оба VAE, Edit Anything и Ripple: HF с закреплёнными ревизиями. Лицензия/доступ проверяются, а не предполагаются.
- Токены: Mac Keychain `h3-r2-account-id`, `h3-r2-access-key-id`, `h3-r2-secret-access-key`, `h3-hf-token`. SSH: ключ, указанный в `SSH_KEY=` установленного `tunnel.sh`. Секреты не помещать в навык, репозиторий, аргументы/вывод команд. На GPU приватные curl/aria2-конфиги 0600, токен передаётся stdin существующим установщиком.
- Если ключи и SSH уже настроены, не задавать вопрос «есть ли доступ» повторно: выполнить безопасную проверку и продолжить. Спрашивать пользователя только о недостающем доступе или неоднозначной цели.
- Загружать непосредственно на GPU, не через Mac. Существующий сценарий запускает архив, H3/HF и R2-дополнения одновременно; aria2 докачка, 16 соединений/файл. Сначала обеспечить место под все отсутствующие веса, архив, распакованный софт и резерв. Не распаковывать в `/dev/shm`.
- SHA-256 архива и каждого веса обязателен; одинаковый размер не доказывает целостность. Не удалять существующие веса. Не останавливать живую загрузку ради другого порядка.
- Не обещать фиксированное время: сообщать измеренную скорость, полученные байты и текущую стадию. Скорость сети не равна скорости рендера.
- Если пользователь просит замер на третьей минуте, взять строку `N мин: получено X ГБ из ~T, сейчас Y МБ/с` из живого лога и дать прогноз по указанной им формуле. Учитывать, что средняя/мгновенная скорость в конце передачи может упасть до нуля во время распаковки и проверки SHA; это не означает остановку установщика. Пока `h3_up.sh` работает, наблюдать за тем же процессом и не запускать второй.

## Короткая проверка и один установщик

Прочитать текущие AGENTS.md и документы проекта. Один раз проверить git status/HEAD, выбранный SSH, руководство Vast, GPU/CUDA, диск, активные задания Mac и ComfyUI. Если данные уже проверены в этом сеансе, повторить только изменившееся.

Перед запуском посмотреть локальные процессы и процессы GPU: нет ли уже `h3_up.sh`, `h3_new_server.sh`, `deploy_h3_new_server.sh`, `install_h3_h200_overlay.sh`, загрузчиков той же модели, включая работу другого агента. Если есть — следить за единственным процессом и его логом, не запускать второй. Не убивать чужой процесс. Собственный дубль остановить вместе с его дочерними/удалёнными процессами, не затрагивая рендер.

Сохранить очереди, референсы, MP4, `~/Library/Application Support/H3 Studio` и `/workspace/h3/ComfyUI/models`. Не менять качество на Turbo/квантизацию, не урезать шаги или разрешение ради скорости.

До изменения туннеля/сервисов временно остановить только dispatch через `PUT /api/queue {"paused":true}`; активный рендер продолжает работать. Дождаться завершения и сохранения MP4, затем пустых `queue_running` и `queue_pending` ComfyUI. Не обходить `needs_reconciliation`. После успешной проверки восстановить согласованное состояние очереди (обычно запустить).

`h3_up.sh` при изменениях в deployment-путях запускает HEAD во временном detached worktree и передаёт туда endpoint, stamp и флаги; рабочие файлы не коммитит и не перезаписывает. Поэтому до запуска убедиться, что необходимые правки уже находятся в HEAD. Не коммитить чужие изменения ради деплоя; если нужная правка только в dirty checkout — объяснить это и попросить только необходимое действие.

## Nebius (обычная VM, с 05.11.2026 основной провайдер — дешевле Vast)

Это не контейнер: вход по cloud-init пользователю (`ubuntu`) ключом `~/.ssh/id_ed25519`, root закрыт, нет supervisor/ffmpeg, CUDA 13.0 вне PATH, репозиторий NVIDIA закреплён apt-pin −1. Порядок:
1. `bash infra/h3_vm_prep.sh --host user@IP` — root по тому же ключу (prohibit-password), пакеты, CUDA 12.8 для XPose отдельным pin только на `*-12-8` (dry-run проверяет, что драйвер не трогается), `/workspace`.
2. `bash infra/h3_up.sh --host root@IP --port 22 --identity ~/.ssh/id_ed25519 --stamp LATEST`.
Логи supervisor вне контейнера пишутся в `/var/log/<program>.log` (признак контейнера — `/.dockerenv`). Диск Nebius ~110 МБ/с на запись: загрузка 150 ГБ ≈ 25 мин, `aria2c` в состоянии D — это ожидание диска, не зависание. VM бывает Preemptible и с лимитом времени: перед долгим рендером проверь срок. RAM 214 ГБ < 256: H3 и энкодер могут перечитываться с диска.

## Требования к серверу и настройки

- Одна NVIDIA GPU ≥ 94 ГБ VRAM, CUDA ≥ 12.8, диск ≥ 600 ГБ, RAM ≥ 256 ГБ (H3 66 ГБ + энкодер 51 ГБ меняются местами в VRAM в каждом задании; при меньшей RAM они перечитываются с диска). Хост/порт — только из запроса пользователя или свежего ответа compute API; исторические значения из `docs/STATE.md` не считать текущим endpoint.
- После установки: шаги по умолчанию 24 (решение пользователя; 50 не предлагать), кэш `safe`, BF16, без turbo-LoRA (`docs/DECISIONS.md`).
- Сверка с репо: `scripts/h3_server_drift.sh`; чистка старых снимков R2 — `infra/h3_r2_prune.sh` только после чтения `LATEST` и сверки SHA.
- Если загрузка уже идёт (процесс aria2/rclone или файлы `.part`) — подхватить её, не запускать вторую. Если `/workspace/h3` нет — не использовать `--skip-base`.

## Готовность и завершение

- Требовать «ИТОГ: всё OK» от `scripts/verify_h3_server.sh` и «Очередь Studio запущена» (либо сохранённую согласованную паузу).
- Для обычного профиля без LTX отсутствие весов/доступности `edit_anything` и `ripple` ожидаемо и не блокирует H3. Проверять `GET http://127.0.0.1:18189/api/video_edit/capabilities` и требовать `available=true`, `missing=[]` только если пользователь отдельно поручил LTX. Туннель и health Studio должны видеть GPU.
- Установленные веса и валидный граф не равны принятому MP4. Если пользователь разрешил тестовый ролик, выполнить ровно согласованный сценарий (обычно 1 фото, короткий текст, 5 секунд), дождаться MP4 и проверить результат. Не повторять дорогую генерацию без причины.
- Если пользователь поручил сохранить новый образ: `bash infra/h3_r2_push.sh --host root@HOST --port PORT`. Требовать «ВЫГРУЖЕНО», проверить новый `LATEST`, размер/SHA архива, число весов и полноту SHA-описи; не выдавать upload за полный restore-тест.
- При сбое проверить конкретную стадию и лог. Одно возобновление той же команды, без повторной загрузки корректных весов. При повторе той же ошибки сохранить последние 40 строк в `docs/JOURNAL.md` и остановить именно этот путь; не делать бесконечных попыток. Явное разрешение пользователя исправить причину позволяет отдельное адресное исправление.
- Обновить `docs/STATE.md` (сервер, deployed commit, R2 LATEST) и добавить строку в `docs/CHANGELOG.md`: выбранный сервер, SHA/проверки, MP4 если был, новый snapshot если был, реальные ограничения. Сырые логи — в `logs/`. Коммитить только свою запись.

## Отбор весов перед следующим развёртыванием (проверено 2026-10-09)

Проверять текущую опись R2 и соответствие активным графам, а не восстанавливать все старые файлы вслепую. В master удалён structural path ControlNet/SDPose/RT-DETR/Depth-Anything; эти веса не нужны для обычного H3. Отдельный FL2VA, Qwen-Image 2.1 и SeedVR2 7B — только выбранные эксперименты, не добавлять по умолчанию. Qwen 8B активен; 27B удалён из восстановления и overlay (6eb8c55), qwen-next-venv на сервере удалён — не возвращать без решения пользователя (`H3_SCENARIST_27B=0`). Не удалять их на существующем сервере.

Текущий H3_BANNED_WEIGHTS_RE исключает лишь few-step H3 LoRA (turbo/hyperflow/lightx2v/taomate/dmad/fasth3/Nstep); это не полный фильтр устаревших весов. Нельзя обещать минимальный набор при запуске неизменённого h3_up.sh со старой описью. SAM2 убран из интерфейса замены героя, но backend keep_people/маски его ещё используют — не исключать по одному изменению UI. ACE-Step turbo — аудиомодель, не запрещённая H3 Turbo LoRA. FP8 Qwen Director/ключевого кадра и FP16 SeedVR2 в текущем installer не считать запрещёнными вариантами основного H3 BF16 автоматически.

LTX/Ripple — отдельный сценарий и ставится только по новой явной просьбе; прежние тесты не меняют стандартный режим без LTX. Context-IR и метрики FirstBlockCache развёртывать из актуального согласованного HEAD поверх файлового снимка. Новый адрес GPU каждый раз брать из запроса пользователя или свежего compute API.
